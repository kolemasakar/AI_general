# Аналіз методички «Автономна продуктова компанія на базі Codex»

## 1. Загальна оцінка

Методичка є якісним і концептуально зрілим описом керованої автономної розробки програмного продукту. Її головна перевага — автономність трактується не як відсутність контролю, а як робота всередині наперед визначеного контуру: цілей, повноважень, даних, середовища, критеріїв якості та стоп-правил.

**Підсумкова оцінка: 8/10.**

- Як система управління автономною розробкою — дуже сильний документ.
- Як практична інструкція безпосередньо для Codex — поки недостатньо конкретний.
- Як модель повноцінної автономної продуктової компанії — назва дещо ширша за фактичний зміст.

## 2. Що фактично описує документ

Методичка формує багаторівневу систему:

- власник продукту визначає цілі, межі та допустимий ризик;
- оркестратор розкладає роботу на незалежні потоки;
- виконавці працюють у власних зонах відповідальності;
- інтегратор приймає зміни у визначеній послідовності;
- QA або synthetic user незалежно перевіряє результат;
- зовнішні та незворотні дії залишаються за людиною.

Це не просто схема багатoагентної роботи. Це модель керованої передачі частини повноважень агентам зі збереженням відповідальності власника продукту.

## 3. Найсильніші сторони

### 3.1. Чіткі межі автономності

Правильно визначено, що агент не повинен самостійно:

- змінювати бізнес-пріоритет;
- приймати юридичні, цінові або брендові рішення;
- виконувати production deployment;
- використовувати реальні дані як тестові;
- маскувати неперевірений результат під готовий.

Це захищає систему від найбільш небезпечного сценарію: технічно активного, але неконтрольованого агента.

### 3.2. Принцип одного автора

Правило одного писальника для schema, API-контрактів, міграцій, dependency manifests, CI та entrypoint-файлів є практично правильним.

Основні проблеми багатoагентної розробки зазвичай виникають не через низьку якість окремого коду, а через одночасні несумісні зміни спільних контрактів.

### 3.3. Правильна система доказів

Розподіл результатів на:

- `passed`;
- `failed`;
- `not_run`;
- `inconclusive`

є дуже вдалим.

Особливо важливе правило: `not_run` не можна переформулювати як успіх. Це запобігає типовій помилці ШІ — логічно домалювати результат, якого фактично не перевіряли.

### 3.4. Наявність quality gates

Послідовність specification → architecture → implementation → integration → verification → local release → production release створює керовану систему переходів.

Правильно зазначено, що наявність коду наступного етапу не означає завершення попереднього gate.

### 3.5. Незалежний synthetic user

Відокремлення перевіряльника від виконавця є сильним рішенням.

Агент, який реалізував функцію, часто оцінює її через власні припущення. Незалежний synthetic user перевіряє спостережувану поведінку продукту, а не внутрішню логіку реалізації.

### 3.6. Хороша структура вхідного ТЗ

Definition of Ready, паспорт ТЗ та статуси «зелений / жовтий / червоний» можна практично використовувати як механізм допуску задачі до автономної реалізації.

## 4. Основні недоліки

### 4.1. Документ описує переважно автономну software delivery system

Методичка добре охоплює:

- software delivery;
- управління репозиторієм;
- тестування;
- інтеграцію;
- локальний і production release.

Для повноцінної продуктової компанії бракує окремих контурів:

- аналізу ринку;
- перевірки проблеми користувача;
- конкурентного аналізу;
- ціноутворення;
- маркетингу;
- продажів;
- підтримки користувачів;
- продуктової аналітики;
- фінансової моделі;
- управління портфелем продуктів.

Точніша назва поточної версії:

> **Керована автономна система розробки програмного продукту на базі Codex.**

### 4.2. Недостатньо конкретики щодо Codex

У назві Codex є центральним елементом, але документ майже не пояснює:

- як створюються робочі сесії;
- як передається контекст;
- як Codex читає репозиторій;
- як організовуються worktree;
- які дозволи має кожен агент;
- як виглядають prompts оркестратора;
- як агенти повертають результати;
- як відновлюється робота в новій сесії;
- як блокуються небезпечні команди;
- як контролюються витрати часу, токенів та API.

Тобто описана організаційна модель, але ще не описаний її конкретний механізм виконання.

### 4.3. Немає формальної моделі станів

Документ використовує gates, але не визначає єдину state machine задачі.

Базовий варіант:

```text
PROPOSED
→ READY
→ ASSIGNED
→ IN_PROGRESS
→ READY_FOR_REVIEW
→ VERIFIED
→ INTEGRATED
→ RELEASE_CANDIDATE
→ RELEASED
```

Окремо потрібні стани:

```text
BLOCKED
REJECTED
SUPERSEDED
INCONCLUSIVE
ROLLBACK_REQUIRED
```

Без формальної моделі оркестратор може по-різному трактувати завершеність задач.

### 4.4. Недостатньо описано відновлення контексту

Для довгих проєктів необхідно визначити:

- які файли читаються на початку нової сесії;
- як агент визначає поточну фазу;
- як підтверджується доступ до GitHub або локального репозиторію;
- як відновлюються відкриті рішення;
- як виявляється розбіжність між документацією і фактичним кодом;
- який документ є точкою входу.

Recovery protocol має бути обов’язковою частиною системи, а не додатковою рекомендацією.

### 4.5. Немає кількісних критеріїв

Формулювання «тести проходять», «середовище відтворюється» та «критичні сценарії перевірені» правильні, але недостатньо формальні.

Доцільно визначити:

- допустимий відсоток невиконаних тестів;
- мінімальне покриття критичних модулів;
- максимальну кількість відкритих дефектів;
- допустимий час запуску;
- performance budgets;
- максимальну кількість повторних спроб;
- максимальну вартість автономного циклу;
- час до ескалації blocker.

### 4.6. Недостатньо деталізована система ескалації

Зазначено, коли потрібно зупинитися, але не визначено:

- кому саме передається питання;
- у якому форматі;
- які варіанти агент повинен підготувати;
- чи може виконуватися інша незалежна робота;
- коли blocker вважається вирішеним;
- хто повертає задачу в роботу.

Рекомендований формат ескалації:

- факт;
- причина блокування;
- вплив;
- доступні варіанти;
- рекомендація;
- необхідне рішення власника.

### 4.7. «Перший запуск за 30 хвилин» надто оптимістичний

За 30 хвилин реально:

- сформулювати mission;
- провести первинний baseline;
- визначити перший вертикальний зріз;
- створити чернетки task charter.

Але перевести реальний проєкт у зелений статус, визначити контракти, ownership, fixtures і quality gates за цей час зазвичай неможливо.

Точніша назва розділу:

> **Початкове налаштування за 30 хвилин.**

## 5. Рекомендації для версії 0.2

### 5.1. Додати Codex Runtime Model

Описати:

- типи сесій;
- права доступу;
- worktree policy;
- правила commit;
- передачу результатів;
- відновлення контексту;
- обмеження команд.

### 5.2. Додати єдину state machine

Окремо визначити:

- стани проєкту;
- стани задачі;
- стани перевірки;
- стани релізу;
- дозволені переходи.

### 5.3. Визначити стандартну структуру керуючих файлів

```text
/AI
  MISSION.md
  CURRENT_STATE.md
  TASK_REGISTER.md
  DECISION_LOG.md
  AUTHORITY_ENVELOPE.md
  SOURCE_OF_TRUTH.md
  QUALITY_GATES.md
  RISK_REGISTER.md
  RELEASE_STATUS.md
```

### 5.4. Додати готові prompts

Потрібні шаблони для:

- запуску оркестратора;
- baseline-аудиту;
- створення task charter;
- виконання feature slice;
- незалежного QA;
- інтеграції;
- recovery після зміни чату.

### 5.5. Додати матрицю повноважень

| Дія | Автоматично | Після перевірки | Тільки власник |
|---|---:|---:|---:|
| Читання репозиторію | Так | — | — |
| Локальні тести | Так | — | — |
| Створення гілки | Так | — | — |
| Merge у main/master | — | Так | — |
| Міграція даних | — | Так | Іноді |
| Production deploy | — | — | Так |
| Зовнішнє повідомлення | — | — | Так |

### 5.6. Додати Recovery Protocol

На початку нової сесії агент повинен:

- перевірити доступні конектори;
- знайти репозиторій;
- прочитати основні керуючі документи;
- перевірити `git status` і останні commits;
- зіставити документацію з кодом;
- визначити останній підтверджений gate;
- продовжувати лише після відновлення фактичного стану.

### 5.7. Додати наскрізний практичний приклад

Приклад повинен показувати:

- початкову ідею;
- заповнене ТЗ;
- dependency graph;
- кілька task charter;
- результати агентів;
- конфлікт контракту;
- інтеграцію;
- evidence pack;
- local release;
- рішення власника щодо production.

Такий приклад перетворить концептуальну методичку на практичний playbook.

## 6. Підсумковий висновок

Методичка має правильну архітектурну основу. Найсильніші її частини — межі автономності, ownership, quality gates, evidence та stop rules.

У поточному вигляді документ добре підходить як верхньорівнева конституція автономного проєкту. Для безпосереднього запуску через Codex потрібен нижній операційний рівень: конкретні команди, prompts, стани, файли, дозволи та recovery-процедури.

Найкращий напрям розвитку — не розширювати текст загальними принципами, а додати виконуваний операційний протокол.

Версія 0.1 — це не готова автономна компанія, але вже сильний фундамент, на якому таку систему можна побудувати.
